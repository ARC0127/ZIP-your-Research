# Resource-proportional execution (active profile v1)

This profile applies to the v1.7.0 suite and its installed skill entrypoints.
It takes precedence over broad default loading, companion-skill, repetition,
intake, and recurring status-banner wording in retained components. It does not override the user's
instructions, host policy, explicit approvals, or scientific evidence rules.

## Choose work by the requested result

- Complete every requested deliverable. Reducing overhead does not authorize
  a smaller task, an outline in place of execution, or an unverified success.
- Start with one primary skill. Read its applicable output contract and the
  source material needed for the decision. Load another skill only for a
  distinct unresolved obligation. A list of related skills is navigation,
  not a requirement to execute them all.
- For local wording changes, use the relevant writing skill. Use a proof
  engine when mathematical validity or a proof obligation is at issue. Use
  global writing/logic audits for integrated manuscript work or an explicit
  request. Preserve frozen claims, formulas, values, and citations in all modes.
- Keep full protocols available for explicitly requested full workflows.
  Archived modules remain reproducible; their blanket "any task" and
  "must use all companions" wording is scoped by this profile.

## Load context progressively

- Skill descriptions identify a capability and its actual trigger. Keep
  substantial protocols in references; do not inline a second copy in SKILL.md.
- Read the selected protocol once while that content remains available and
  valid. Search an index or manifest for the selected entry; do not preload the
  catalog, every engine, all boot files, or every referenced document.
- Read additional material when an unresolved question requires it. Reinspect
  mutable facts when needed; never invent a source check or claim an unread
  protocol was followed. Do not rerun a search just to reproduce a status label.

## Reasoning, tools, and workers

- Ordinary replies, including Codex commentary and final answers, have no status
  banner. Show relevant status fields only on user request or explicit diagnostic
  opt-in; do not repeat unchanged fields. This overrides legacy every-message
  banner instructions, including S430 display rules. Strict ZIP intake and
  Mode Lock confirmation remain required. Full field definitions are available
  in `boot/00_RESPONSE_STATUS_BANNER_v1.7.0.md` only when needed.
- Match analysis to the actual uncertainty, consequence, and requested rigor.
  Explain the conclusion and decisive evidence without narrating repeated
  deliberation. This profile does not change the host's model or reasoning effort.
- Default to the current agent. Ordinary authoritative search, a difficult
  question, and the availability of collaboration tools do not by themselves
  select S660 or authorize a team.
- Use S660 for an explicitly selected multi-agent research or independent
  cross-examination workflow. Preserve its real-worker capability checks.
  Never describe a single-agent run as a completed multi-agent evaluation.
- When delegation is authorized, assign a concrete independent deliverable
  alongside useful local work. Supply the necessary context and return compact
  evidence. Add workers only for uncovered obligations, not to fill slots;
  do not recursively delegate or repeat reviews without a task-specific reason.
- Batch independent tool reads where supported. Each new search, test, review,
  or worker round should resolve an identified remaining question. After the
  requested result and required checks are complete, deliver it.

## Intake, steering, and approval

- The active strict startup is `boot/00_BOOTSTRAP_PROTOCOL_v1.7.0.md`. Generate
  working Mode Lock Markdown/JSON and migration prompts with suite v1.7.0 using
  its current templates. Do not adopt a retained module's version as session
  identity. Existing confirmed scope survives a version-only normalization.
- ZIP-only startup and user-selected strict Mode Lock workflows retain their
  explicit CONFIRM requirement. Calling an atomic skill does not start that
  workflow again. Reuse an existing lock and already granted authorization.
- Corrections, added references, progress questions, and implementation details
  within the same objective are in-scope steering. Incorporate them, answer
  briefly when appropriate, and continue. Do not demand a new lock for them.
- A real change of objective or authorization boundary follows the existing
  change-confirmation protocol. Ask only for missing information that affects
  the result or authority; do independent authorized work while waiting.
- Preserve explicit approval for publication, secret handling, persistent
  memory activation, and other protected actions. A request for a plan or an
  audit is not permission to carry out its recommendations.

## Verify the kind of change actually made

- Packaging and maintenance: check preserved source content, reference closure,
  generated artifacts, relevant routing regressions, installation, and rollback.
- Agent-behavior claims: compare baseline and candidate on fixed tasks with the
  same model/settings and score completion quality as well as calls and usage.
  Report measured bytes separately from tokens; missing telemetry is UNKNOWN.
- Scientific-capability claims: retain the applicable held-out, mutation,
  counterfactual, and scientific evaluation requirements. Structural checks
  alone cannot promote a scientific or behavioral improvement claim.
- Do not manufacture a research benchmark for an entrypoint maintenance edit.
  Do not broaden or repeat passing checks without a new change, failure, or
  unresolved concern. Full requested research and required checks still apply.

The separate claim skill's fresh-literature and coaching contracts are not
changed by this profile. Suite identity remains v1.7.0; profile version is v1.
