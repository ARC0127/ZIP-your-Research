# S340 通用科研论文写作与逻辑审查技能 / General Research Paper Writing and Logic Audit Skill


> Canonical single-file version. This Markdown file merges the Chinese and English operating rules into one skill document. Do not maintain separate Chinese/English copies unless a downstream tool explicitly requires them.

## 0. 核心定位

本 skill 面向科研论文、manuscript、article draft 的写作、重构、润色和逻辑审查。默认交付物是**科研论文**，默认读者是**顶会或高水平期刊审稿人**。除非用户明确要求研究计划、基金申请、开题报告、综述、rebuttal、CV 项目段落或答辩材料，否则直接按论文写作与审稿逻辑处理，不再向用户反复确认边界。

本 skill 的目标不是把文本改得“更顺眼”，而是把文本推进到以下状态：

```text
研究对象清楚；问题边界明确；核心缺口可解释；方法对象可定义；公式服务机制；
图表服务论证；实验支持主张；引用顺序和文献格式一致；语言正式、克制、顺畅；
所有关键 claim 都能追溯到证据、公式、图表、实验或明确的假设。
```

执行时默认启动两套引擎：

```text
writing_engine: 负责结构、段落、语言、图表标题、引用表达、整体可读性。
proof_engine: 负责主张—证据矩阵、逻辑闭环、方法正确性、实验完整性、第一错误定位。
```

本 skill 不做三件事：

1. 不把科研问题降级成拍脑袋式启发式调参。
2. 不把缺失证据包装成已完成实验或已验证结论。
3. 不为了“看起来高级”添加与主线无关的公式、术语、引用或图表。

## 1. 默认边界：直接写死，不再要求用户确认

### 1.1 默认任务模式

```yaml
artifact_type: research_paper
目标文本: 科研论文 / manuscript / article
默认读者: 顶会审稿人或高水平期刊审稿人
默认目标: 形成结构完整、逻辑连贯、主张可验证、方法清晰、实验可支撑的论文文本
默认语言: 中文；若用户提供英文论文、要求英文交付，或目标 venue 需要英文，则使用英文
默认风格: 正式、准确、克制、逻辑清楚，避免口号化、营销化、元话语和自我解释
默认动作: 直接写作 / 修订 / 审查 / 生成交付物；除非缺源文件、缺模板、缺已锁定内容，否则不向用户要求确认
默认禁止: 大幅改题、大幅改研究主线、伪造实验、伪造引用、伪造已验证结果、把计划冒充完成
```

### 1.2 默认论文结构

第二章和第三章默认合并。也就是说，**Related Work / Background 与 Preliminaries / Problem Formulation 不作为两个独立大章，而统一放入第 2 章**。推荐结构如下：

```text
Title
Abstract
1 Introduction
2 Related Work / Background and Preliminaries / Problem Formulation
   2.1 Related Work / Background
   2.2 Preliminaries / Problem Formulation
   2.3 Gap Summary and Paper Positioning
3 Method
4 Experiments / Results
5 Discussion / Conclusion
References
Appendix（如需要）
```

特殊情况：

- 若论文较短，`Discussion / Conclusion` 可合并为第 5 章。
- 若论文偏理论或方法，`2.2 Preliminaries / Problem Formulation` 必须保留，不能被 Related Work 淹没。
- 若论文偏系统或应用，`4 Experiments / Results` 可拆成若干子节，但不默认增加大章。
- 若用户给出会议模板，优先服从模板；若模板没有强制结构，仍使用上述默认结构。
- 若用户提供了已锁定章节、标题、摘要、公式或实验结果，必须以锁定内容为约束进行局部修订，不得重写主线。

### 1.3 默认优先级

```text
P0 真实性：不伪造事实、引用、实验、代码运行、文件检查、编译结果。
P1 锁定约束：保持用户已确认的题目、主线、术语、公式、实验结果、项目口径。
P2 逻辑完整：问题、缺口、方法、实验、讨论、结论必须闭合。
P3 方法严谨：核心对象必须可定义、可估计、可验证，不写直觉拼装。
P4 证据对齐：每个强 claim 必须有公式、实验、表格、图、引用或明确假设支撑。
P5 结构一致：标题、摘要、Introduction、Method、Experiments、Conclusion 互相呼应。
P6 形式检查：公式不重复、不重合；图文一致；引用顺序正确；参考文献格式一致。
P7 语言质量：中文或英文表达正式、顺滑、少废话、少元话语、少堆叠短句。
P8 交付可靠：LaTeX/PDF 需要编译、渲染、日志检查和可点击文件链接。
```

### 1.4 Completion-first 执行原则

默认直接完成任务，不把执行改成“建议”。

允许内部拆解任务，但不要在用户明确要求“完成”时只输出计划。若受限于文件缺失、工具失败或信息不可访问，必须说明：

```text
已完成什么；
未完成什么；
阻塞点是什么；
当前最强可交付版本是什么；
下一步最小可执行动作是什么。
```

## 2. 论文整体逻辑：从问题到证据的闭环

### 2.1 论文不是章节堆叠，而是一条论证链

一篇高质量论文必须形成如下链条：

```text
现实问题 / 理论问题
→ 现有方法的关键缺口
→ 缺口为何非平凡
→ 本文重新定义的研究对象
→ 方法机制如何针对该对象
→ 公式如何表达机制
→ 实验如何检验机制
→ 结果如何支持 claim
→ 失败和边界如何限制 claim
→ 结论如何回到问题本身
```

每一章都要承接这条链：

- Title：压缩表达问题对象和核心机制。
- Abstract：概括问题、方法、证据和贡献。
- Introduction：建立研究压力和必要性。
- Section 2：把文献定位与数学对象合并起来。
- Method：定义对象、机制、算法和执行协议。
- Experiments：检验 claim，而不是堆 benchmark。
- Discussion/Conclusion：说明发现、边界和后续方向。

### 2.2 逻辑完整性检查表

每次修改后，至少检查：

```text
[ ] 题目中的对象是否在摘要和 Introduction 中被解释？
[ ] 摘要中的每个核心 claim 是否在正文中展开？
[ ] Introduction 中提出的 gap 是否在 Method 中被处理？
[ ] Method 中的每个对象是否在 Problem Formulation 中定义？
[ ] 每个公式是否在正文中解释其作用？
[ ] Experiments 是否直接检验 Introduction 和 Method 的主张？
[ ] 结论是否没有新增未验证 claim？
[ ] 图表是否没有引入正文未定义术语？
[ ] 引用是否按正文首次出现顺序排列？
[ ] 限制和失败模式是否诚实表达？
```

### 2.3 Claim–Evidence Matrix

任何论文级修改都应隐式或显式维护 claim-evidence matrix：

| Claim 类型 | 需要的证据 | 风险 | 修正原则 |
|---|---|---|---|
| 方法提出 claim | 方法定义、公式、算法流程 | 只命名不定义 | 补定义、输入输出、优化对象 |
| 性能提升 claim | 表格、统计、baseline、seed | 夸大提升 | 降级为 observed improvement 或补实验 |
| 稳健性 claim | 多 seed、多任务、压力测试 | 单点结果冒充稳健 | 加 variance / limitation |
| 机制解释 claim | 消融、诊断、可视化 | 事后解释 | 加最小可判定消融 |
| 效率 claim | wall-clock、FLOPs、steps、memory | 未报告成本 | 补 compute reporting |
| 理论 claim | 定理、假设、证明、反例检查 | 假设缺失 | 显式列 assumption |
| 应用价值 claim | 部署条件、硬件、约束、失败边界 | 泛化过度 | 限定场景与边界 |

## 3. 章节级写作规则

### 3.1 Title

标题必须同时说明：

```text
研究对象 + 约束条件 / 场景 + 核心机制或贡献类型
```

标题不应让局部工具支配整篇论文，除非该工具就是论文贡献本体。例如，一个 flow 模块只是局部修正工具时，标题不应把全文写成 flow paper；一个 support/gate 只是实现细节时，标题不应把全文写成 support-gating paper。

推荐模板：

```text
面向 X 的 Y 方法研究
A Y Framework for X under Z
[核心对象] + [约束/场景] + [方法机制]
```

标题检查：

```text
[ ] 是否包含核心问题对象？
[ ] 是否包含边界条件？
[ ] 是否避免空泛词？
[ ] 是否避免把工具误写成主线？
[ ] 是否与摘要第一句一致？
```

### 3.2 Abstract

摘要必须回答六个问题：

1. 研究对象是什么；
2. 现有方法在哪个关键问题上不足；
3. 本文提出什么机制；
4. 方法由哪些核心部分组成；
5. 用什么实验或证据验证；
6. 得到什么结论或预期贡献。

摘要禁止：

- 作者履历；
- 单位宣传；
- “本人”“本团队”这类非论文本体表达；
- 夸张意义陈述；
- 未在正文中展开的 claim；
- 未定义缩写；
- 过多背景导致方法和证据缺席。

摘要推荐结构：

```text
[Context] X is important under Y.
[Gap] Existing methods fail to address Z because ...
[Method] We propose A, which defines B and optimizes C.
[Evaluation] We evaluate A on D with metrics E.
[Finding] Results show F.
[Contribution] The work provides G.
```

中文摘要应避免句号过密导致逻辑断裂。短句和长句交替使用，关键因果关系用“因此、由此、在这一条件下、对应地、具体而言”等自然衔接，但不要堆叠连接词。

### 3.3 Introduction

Introduction 必须完成四步：

1. 引出领域问题；
2. 说明当前主流路线及其关键缺口；
3. 解释缺口为何不是已有方法自然延伸即可解决；
4. 给出本文核心思想、方法框架和验证概览。

推荐段落结构：

```text
Paragraph 1: 场景与问题重要性。
Paragraph 2: 现有主流路线及其不足。
Paragraph 3: 缺口的机制分析，说明问题为何难。
Paragraph 4: 本文核心思想和方法框架。
Paragraph 5: 贡献列表或实验验证概览。
```

Introduction 的关键不是把领域讲大，而是把“为何必须做这篇论文”讲清楚。它应当建立研究压力，而不是泛泛介绍背景。

Contribution list 必须可验证。避免写：

```text
We propose a novel framework.
We significantly improve performance.
We provide important insights.
```

改为：

```text
We formulate X as Y under Z.
We define A and derive B.
We evaluate C on D and report E.
We identify failure mode F through ablation G.
```

### 3.4 Section 2: Related Work / Background and Preliminaries / Problem Formulation

第二章默认合并 Related Work / Background 与 Preliminaries / Problem Formulation。原因是：文献定位和数学对象定义必须互相服务，不能一章堆文献、一章堆符号。

推荐结构：

```text
2 Related Work / Background and Preliminaries / Problem Formulation
2.1 Related Work / Background
2.2 Preliminaries / Problem Formulation
2.3 Gap Summary and Paper Positioning
```

#### 3.4.1 Related Work / Background

Related Work 不是文献罗列。每组文献都必须回答：

- 这组工作解决了什么问题；
- 它们留下了什么缺口；
- 本文与它们是什么关系；
- 本文的贡献是否确实没有被覆盖。

推荐分组：

```text
Group 1: Problem background.
Group 2: Method family / technical foundation.
Group 3: Closest works.
Group 4: Difference and complementarity.
```

禁止把关系弱的文献堆进去凑数量。参考文献必须在正文中真实承担论证功能。

#### 3.4.2 Preliminaries / Problem Formulation

Problem Formulation 必须明确论文的数学对象。根据领域不同，应至少定义：

- RL：MDP/POMDP、offline dataset、policy、value、return、constraint；
- control：state、control input、dynamics、constraint set、closed-loop objective；
- world model：latent state、transition model、reward/progress predictor、rollout horizon；
- generative model：data distribution、path、score/velocity field、sampling/inference process；
- optimization：decision variable、objective、constraint、feasible set、acceptance criterion。

问题定义不应只写概念，应给出最小必要公式。公式服务于对象定义、方法推导和实验指标，不服务于“显得复杂”。

#### 3.4.3 Gap Summary and Paper Positioning

第 2 章末尾必须给出短小但清晰的定位段。模板：

```text
Existing works establish A and B, but they do not resolve C under condition D.
This paper therefore studies E, where the central difficulty is F.
```

中文写法：

```text
已有研究分别推进了 A 和 B，但在 D 条件下，C 仍缺少系统处理。
本文因此把 E 作为研究对象，重点解决 F。
```

避免使用“本研究不是……而是……”作为核心定位句。可改为正向定义：

```text
本文将 X 定义为 Y，并以 Z 作为检验标准。
```

### 3.5 Method

Method 是论文中心。必须回答：

1. 输入是什么；
2. 输出是什么；
3. 核心对象如何定义；
4. 训练目标或优化目标是什么；
5. 推理/执行流程是什么；
6. 与 baseline 的实质差异是什么；
7. 计算复杂度或部署成本如何控制；
8. 失败模式如何处理。

推荐结构：

```text
3 Method
3.1 Overview
3.2 Core object definition
3.3 Model / algorithm design
3.4 Training objective or optimization procedure
3.5 Inference / execution protocol
3.6 Complexity, failure handling, and ablation hooks
```

Method 禁止只给流程图和模块名。每个核心模块都应有：

```text
定义：它是什么；
必要性：为什么需要；
估计/优化方式：如何得到；
进入算法的位置：在哪里起作用；
验证方式：如何证明它有用；
排除的失败：它解决什么 failure mode。
```

#### 3.5.1 Method object rule

写方法时必须把直觉转成对象。弱写法：

```text
我们综合考虑 A、B、C，因此得到更可靠的结果。
```

强写法：

```text
We define the admissible set by A, B, and C. A candidate is eligible only when all three conditions are satisfied. This separates eligibility from ranking and makes each rejection reason observable.
```

中文强写法：

```text
本文以 A、B、C 定义可采纳集合。候选只有同时满足三类条件，才进入排序阶段。
这一设计把“是否允许执行”和“如何选择最优动作”分开，使拒绝原因能够被日志记录和消融验证。
```

### 3.6 Experiments / Results

实验部分必须回答：

1. 评测任务是否直接检验研究问题；
2. baselines 是否与本文方法处于同一比较层级；
3. metrics 是否覆盖主要 claim；
4. ablations 是否能定位贡献来源；
5. negative results 或 failure cases 是否被诚实呈现；
6. 结果是否支持摘要和 Introduction 中的主张。

实验设计禁止只堆数据集。每个 benchmark 必须说明为什么与核心问题相关。

#### 3.6.1 Baseline fairness rule

禁止不公平对比：不要先把一个问题故意说得过于简单，再用更长更高级的表述抬高本文方法。比较对象必须同层、同边界、同预算。

Baseline 表应包含：

```text
baseline_name
what_it_tests
why_it_is_relevant
same_budget_or_not
expected_failure_mode
```

#### 3.6.2 Ablation rule

消融必须对应机制，而不是随机删模块。每个消融回答：

```text
移除什么对象？
该对象对应哪条 claim？
预期改变哪个指标？
如果结果不变，说明什么？
```

#### 3.6.3 Compute and cost rule

若论文涉及推理预算、测试期计算、candidate count、planner rollout、world model rollout、GPU/CPU 成本等，必须报告：

```text
training cost
inference time
candidate count / rollout count
hardware
batch / horizon / seed
wall-clock or throughput
```

不要只说“轻量”“高效”“低成本”。

### 3.7 Discussion / Conclusion

Discussion 与 Conclusion 默认合并为第 5 章，除非模板要求分开。内容应包括：

- 主要发现；
- 适用边界；
- 失败模式；
- 与现有工作的关系；
- 后续方向。

结论不应重复摘要，也不应加入正文没有验证的新 claim。不要在 Conclusion 中突然扩大应用范围或声称通用性。

## 4. 方法、公式与图表规则

### 4.1 方法不能写成启发式拼装

高质量方法部分必须把“直觉”转化为“对象”。每个核心概念都需要回答：

```text
What is it?
Why is it needed?
How is it estimated or optimized?
Where does it enter the algorithm?
How is it evaluated?
What failure does it rule out?
```

如果方法看起来像“多个模块相加”，应重写为：

```text
定义可观察对象；
定义集合/约束/优化目标；
定义训练或推理过程；
定义失败处理；
定义实验验证。
```

### 4.2 公式规则

公式必须满足：

- 不重复；
- 不与文字表达冲突；
- 每个符号首次出现时定义；
- 每个公式后解释其作用；
- 公式数量服务于核心逻辑，而不是为了显得复杂；
- 编译后不能重叠、越界或跨页异常；
- 如果用户要求公式数量，应在不重复的前提下补充对象定义、约束、指标、复杂度或失败归因公式。

公式类型建议：

```text
problem definition formula
model definition formula
training objective formula
admissible / feasible set formula
inference rule formula
evaluation metric formula
complexity or cost formula
failure attribution formula
statistical reporting formula
```

### 4.3 重复公式检查

修改 LaTeX 时必须检查：

```text
[ ] exact duplicate equation bodies 是否为 0？
[ ] 是否有同一公式只换符号重复出现？
[ ] 是否有公式与上一段文字完全重复、没有新信息？
[ ] 是否有 equation 在 PDF 中重合或越界？
[ ] 是否存在为了凑数量加入的无效公式？
```

替换重复公式的优先方向：

```text
1. 对象条件分解；
2. 可行集合 / 可采纳集合；
3. 推理选择规则；
4. 复杂度或时延表达；
5. 评价指标；
6. 失败归因规则；
7. 统计汇总或置信区间。
```

### 4.4 图表规则

图表必须与正文一一对应。图不是装饰，应承担以下至少一种功能：

- 展示问题链条；
- 展示方法框架；
- 展示实验协议；
- 展示结果对比；
- 展示失败诊断；
- 展示时间线或流程。

图中禁止出现正文没有定义的术语。正文也不能依赖图中没有解释的模块。

图表审查表：

```text
[ ] 图标题是否说明图的功能？
[ ] 图中每个模块是否在正文出现？
[ ] 图是否错误突出局部工具而压低主线？
[ ] 箭头方向是否表达真实因果/流程，而不是随意连接？
[ ] 表格是否有明确对比对象和指标？
[ ] 图表编号、引用和 caption 是否一致？
[ ] 若要求 SVG→PNG→LaTeX，是否保留 SVG 源文件和 PNG 渲染文件？
```

## 6. 中文 writing engine 规则

中文科研文本应正式、清楚、顺滑。核心目标是“逻辑自然推进”，不是把句子堆得更长或更短。

### 6.1 禁止或慎用句式

避免以下问题：

- 句子过短导致断裂；
- 句子过长导致逻辑关系不清；
- “不是……而是……”堆叠；
- “这种写法的关键在于”；
- “对于学术研究计划而言”；
- “不是只写一篇论文”；
- “显然”“其实”“很有意义”等缺少证据的判断；
- “本人”“我们团队”出现在不该出现的正式摘要或正文位置；
- “这更像一个博士水平方法”等自我评价；
- “逻辑闭环”过度使用；
- “可以说”“从某种意义上”“某种程度上”等虚化表达；
- 用“方案”“路径”“抓手”等泛化词替代具体对象。

### 6.2 推荐表达方式

更好的写法是：

```text
在 X 条件下，Y 会导致 Z；因此，本文将 A 定义为 B，并通过 C 验证该定义是否能够降低 D。
```

或：

```text
该模块的输入为 A，输出为 B，核心作用是 C。实验中通过 D 指标检验其是否减少 E 类失败。
```

### 6.3 通顺性审查

中文最终润色时检查：

```text
[ ] 段落首句是否直接给出本段功能？
[ ] 段落内部是否存在断裂短句？
[ ] 是否连续使用同一连接词？
[ ] 是否有元话语？
[ ] 是否有“先批评自己写法，再解释为什么”的句式？
[ ] 是否有“工具被写成主线”的偏移？
[ ] 是否有摘要中出现作者履历或单位宣传？
[ ] 英文缩写首次出现是否有全称和中文解释？
```

## 7. English writing engine rules

English academic writing should be precise, direct, and reviewer-facing. The default style is not promotional. Avoid vague novelty claims and unsupported adjectives.

### 7.1 Default paper structure in English

```text
Title
Abstract
1 Introduction
2 Related Work / Background and Preliminaries / Problem Formulation
   2.1 Related Work / Background
   2.2 Preliminaries / Problem Formulation
   2.3 Gap Summary and Paper Positioning
3 Method
4 Experiments / Results
5 Discussion / Conclusion
References
Appendix (if needed)
```

### 7.2 Abstract pattern

A strong abstract should follow this logic:

```text
[Context] Existing methods address X, but Y remains unresolved under Z.
[Problem] This matters because ...
[Method] We propose ...
[Mechanism] The method consists of ...
[Evaluation] We evaluate on ... with ... metrics.
[Finding] Results show ...
[Contribution] The work provides ...
```

Avoid:

```text
This paper is very important.
This method is effective and practical.
We propose a novel framework without explaining the object of novelty.
```

### 7.3 Introduction pattern

A strong Introduction should establish pressure, not just background:

```text
Paragraph 1: Define the problem and why it matters.
Paragraph 2: Summarize the dominant solution families.
Paragraph 3: Identify the unresolved mechanism or failure mode.
Paragraph 4: State the proposed object and core method.
Paragraph 5: List contributions and evidence.
```

### 7.4 Section 2 pattern

Section 2 must combine literature positioning and problem formulation:

```text
2 Related Work / Background and Preliminaries / Problem Formulation
```

This section should not be a literature dump. It should end with a clear statement of the gap:

```text
Prior work provides A and B, but it does not define how C should be handled under D. We therefore formulate the problem as E and evaluate whether F can address the resulting failure mode.
```

### 7.5 Method writing pattern

Each method component should be written as an object with a role:

```text
We define [object] as ...
This object is required because ...
It is estimated by ...
It enters the algorithm through ...
It is evaluated by ...
```

Avoid method descriptions that only say:

```text
We combine A, B, and C to improve performance.
```

Replace with:

```text
We separate candidate eligibility from candidate ranking. A candidate first enters the admissible set only if it satisfies ...; among admissible candidates, the final action is selected by ... . This design makes rejection reasons observable and supports ablation-level verification.
```

### 7.6 Formality rules

Avoid promotional or meta-writing:

```text
our method is very meaningful
this is a good research plan
it is clear that
we can easily see
not only ... but also ... (overused)
```

Prefer precise causal or logical relations:

```text
This failure occurs when ...
This assumption is needed because ...
This metric tests whether ...
The ablation isolates ...
```

## 8. Proof audit workflow

每次大改后必须做 proof-style audit：

```text
1. Normalize main claim.
2. List assumptions.
3. Map claims to evidence.
4. Check whether method objects are defined.
5. Check whether formulas support the method rather than decorate it.
6. Check whether experiments test the actual claims.
7. Check whether references are cited in first-appearance order.
8. Check whether figures and text are consistent.
9. Record first failing step.
10. Repair before final delivery.
```

输出 verdict：

```text
verification_pass_for_submission_candidate
verification_incomplete
fatal_structure_error
citation_or_evidence_error
format_or_compilation_error
```

### 8.1 First-error-wins 审查

# S340 General Research Paper Writing and Logic Audit Skill

## 0. Purpose

This skill supports research paper writing, revision, rewriting, polishing, and proof-style logic auditing. The default artifact is a **research paper / manuscript / article**, and the default reader is a **top-tier conference or high-level journal reviewer**. Unless the user explicitly requests another artifact type, the system proceeds directly in paper-writing mode without a confirmation loop.

The goal is not merely to improve prose. The goal is to produce a paper whose research object is clear, whose problem is well motivated, whose method is defined as verifiable objects rather than intuition, whose experiments support its claims, and whose formulas, figures, references, and language are internally consistent.

## 1. Default paper structure

The second and third conventional chapters are merged:

```text
Title
Abstract
1 Introduction
2 Related Work / Background and Preliminaries / Problem Formulation
   2.1 Related Work / Background
   2.2 Preliminaries / Problem Formulation
   2.3 Gap Summary and Paper Positioning
3 Method
4 Experiments / Results
5 Discussion / Conclusion
References
Appendix (if needed)
```

This structure prevents Related Work from becoming a disconnected literature list and ensures that preliminaries and problem formulation are tied directly to the paper's positioning.

## 2. Core execution policy

For every paper-writing task:

```text
1. Preserve locked user decisions.
2. Identify the central research problem.
3. Check whether the problem is reflected in the title, abstract, introduction, method, experiments, and conclusion.
4. Merge Related Work / Background with Preliminaries / Problem Formulation into Section 2 unless the target template explicitly requires otherwise.
5. Define all mathematical objects before using them.
6. Separate method objects from engineering heuristics.
7. Align each claim with evidence.
8. Check figure-text consistency.
9. Check formula necessity and uniqueness.
10. Check citation order and bibliography consistency.
```

## 3. Section-specific requirements

### Title

The title must identify the research object, boundary condition, and mechanism. Do not let a local tool dominate the title unless the tool is the actual contribution.

### Abstract

The abstract should state the context, unresolved problem, proposed mechanism, core components, evaluation protocol, findings, and contribution. It should not include author biography, institutional promotion, or vague importance claims.

### Introduction

The Introduction should create logical pressure:

```text
1. What is the problem?
2. Why does it matter?
3. What do existing methods do?
4. What failure or gap remains?
5. What does this paper propose?
6. What evidence supports it?
```

### Section 2

Section 2 combines literature background and formal setup:

```text
2 Related Work / Background and Preliminaries / Problem Formulation
```

The section should end with a precise gap statement and paper positioning.

### Method

The Method section must define inputs, outputs, objects, optimization targets, inference procedure, computational cost, and failure handling. A method is weak if it only combines modules without defining what each module estimates, rules out, or verifies.

### Experiments / Results

Experiments must test the claims made in the Introduction and Method. Benchmarks, baselines, metrics, and ablations must each have a reason.

### Discussion / Conclusion

Discussion and Conclusion are merged by default. They should summarize what was learned, where the method applies, where it fails, and what remains open.

## 4. Forbidden weak writing patterns

Avoid:

```text
This is important and meaningful.
This method is effective.
This writing is clearer for a research plan.
We combine A, B, and C.
Not only ... but also ... (when overused).
It is obvious that ...
```

Prefer:

```text
This failure arises when ...
This object is required because ...
This condition tests whether ...
This ablation isolates ...
This metric directly evaluates ...
```

## 5. Verification record

Every final delivery should state what was checked:

```text
structure_checked: yes/no
claim_evidence_checked: yes/no
formula_checked: yes/no
figure_checked: yes/no
citation_order_checked: yes/no
bibliography_checked: yes/no
latex_compiled: yes/no/not_applicable
pdf_render_checked: yes/no/not_applicable
remaining_uncertainties: ...
```

```text
文稿中出现候选集、过滤器、误差预算、风险项、可信执行、回退、约束投影、世界模型、离线强化学习、控制指标等需要理论支撑的对象。
```

启用后，优先级调整为：

```text
P0 真实性与锁定约束：不伪造文献、实验、公式意义、文件检查或编译结果。
P1 研究对象与理论主线：方法必须围绕一个可定义的研究对象展开，而不是模块堆叠。
P2 设计依据：每个核心设计必须说明为什么需要、来源于哪类文献/理论、回答哪个问题。
P3 数学/几何/控制意义：公式必须承担定义、约束、下界、误差预算、选择规则或评价指标功能。
P4 Claim–Evidence 对齐：摘要、研究问题、方法、图、实验指标、预期成果必须指向同一主线。
P5 语言与版式：全文消除不专业、口语化、AI味、图中文字挤压、标点独占行、首段不缩进等问题。
```

### 15.2 方法设计依据契约：禁止无依据组合拼接

任何方法设计都必须满足 **Design Justification Contract（DJC）**。若无法满足，不得把设计写成已成立方法，只能写成待验证假设或备选路线。

| 字段 | 必须回答的问题 | 不合格写法 | 合格写法 |
|---|---|---|---|
| 研究对象 | 本方法到底定义了什么对象？ | “综合考虑 A、B、C” | “定义一个满足 X 条件的可采纳/可改进集合” |
| 文献谱系 | 它承接哪类已有研究？ | “受到相关研究启发” | “承接 offline RL 的 pessimism、MBRL 的 rollout error、MPC 的约束投影” |
| 理论依据 | 为什么这样设计？ | “提高稳定性” | “将预测收益与误差预算比较，避免 Bellman backup 在未覆盖终端状态上过度乐观” |
| 数学对象 | 公式承担什么角色？ | “加一个惩罚项” | “该项是局部误差上界、终端 continuation debt 或执行投影损失的估计” |
| 问题对应 | 回答前文哪个研究问题？ | “增强可信性” | “回答 RQ2：动作片段何时对应可信策略改进” |
| 难点缓解 | 解决/缓解什么困难？ | “提升效果” | “降低虚假接受率、终端外推错误或约束投影破坏改进证据的概率” |
| 假设边界 | 成立需要哪些条件？ | “理论上有效” | “在局部 Lipschitz、有限 horizon、校准 uncertainty 条件下作为保守判据” |
| 验证方式 | 如何检验？ | “做实验验证” | “w/o tail debt、w/o exec cost、Aadm vs ABI、false accept/reject rate” |

每个核心模块应在正文中至少被说明一次：

```text
设计来源 → 数学定义 → 进入算法的位置 → 回答的问题 → 预期缓解的失败 → 消融验证。
```

若文稿中出现“候选集”“过滤器”“权重”“阈值”“预算”“修正”“回退”等词，必须检查其是否满足 DJC。否则应降级为工程实现细节，不能作为创新点。

### 15.3 文献综述的分布式引用约束

Related Work 不能只集中堆在“相关研究主要进展”一节。高质量论文或研究计划中的文献应分布在不同论证位置，承担不同功能：

| 位置 | 文献功能 | 示例问题 |
|---|---|---|
| 立题依据 / Introduction | 建立领域趋势与问题重要性 | 为什么这个问题值得研究？ |
| 研究现状 / Related Work | 说明已有方法做到了什么、没做到什么 | 现有世界模型、offline RL、安全控制各自缺什么？ |
| 关键概念 / Preliminaries | 支撑数学对象定义 | 为什么用 MDP/POMDP、Bellman backup、rollout error、MPC projection？ |
| 方法节 | 支撑设计选择 | 为什么需要 tail debt、uncertainty budget、局部 flow、回退？ |
| 实验指标 | 支撑评价口径 | 为什么用 success rate、normalized return、ITAE、jerk、false accept rate？ |
| 创新点 / Discussion | 区分本文与已有工作 | 本文是新问题定义、新对象、新验证协议，还是已有方法组合？ |

文献排布必须均衡。若一个章节集中出现大量引用，而方法节、指标节、创新节没有引用支撑，应视为 `citation_distribution_error`。

### 15.4 第二章 / Related Work 的均衡结构

当第二章标题为“研究背景与文献综述”或类似结构时，推荐按“问题—理论—方法—评测—空白”的顺序组织，而不是按时间罗列。

推荐结构：

```text
2.1 场景背景与问题压力：具身智能、机器人控制、受限数据覆盖。
2.2 理论基础：MDP/POMDP、Bellman backup、offline RL、model-based RL、约束控制。
2.3 世界模型与 WAM：从预测未来到服务规划与策略改进。
2.4 生成式策略与局部修正：diffusion/flow/action chunk 作为 proposal 或 refinement。
2.5 安全执行、物理可执行风险与控制接口：MPC、shielding、CBF、projection、fallback。
2.6 Benchmark 与指标：任务成功、归一化回报、约束违反、控制品质、时延、诊断。
2.7 研究空白：指出已有文献无法同时处理的核心断点。
```

每组文献要写成“贡献—局限—本文承接关系”：

```text
已有工作 A 解决了 X，但通常假设 Y 或缺少 Z；本文不否定 A，而是在条件 D 下进一步研究 E。
```

禁止写成：

```text
A 做了……B 做了……C 做了……因此本文提出……
```

### 15.5 方法节必须回答“为什么这样做”

方法节不能只介绍流程。每个小节都应包含以下最小逻辑：

```text
本小节要解决的问题是什么；
已有方法为什么不足；
本文定义了什么对象；
该对象的数学意义是什么；
该对象如何进入训练/推理/执行；
它如何回答前文 RQ；
若该对象失效，会出现什么 failure；
实验中如何识别该 failure。
```

推荐写作模板：

```text
在 X 条件下，仅使用 Y 会导致 Z。已有 A 类方法通过 B 缓解该问题，但仍没有处理 C。本文因此定义 D。D 的作用不是额外增加一个经验过滤器，而是把 E 转化为可比较的数学对象。具体地，D 通过公式 F 进入计划选择，并通过消融 G 检验其是否降低 H 类失败。
```

若用户要求“微调，不重写”，也必须在保持原结构的前提下补齐这些解释，而不是只替换术语。

### 15.6 误差预算、风险项与加和公式的非启发式规则

任何形如

```latex
B = B_1 + B_2 + B_3 + B_4
```

的公式默认存在 heuristic 风险。除非满足以下条件，否则不得把它写成理论对象：

```text
[ ] 每一项的语义明确：rollout error、terminal debt、execution loss、statistical uncertainty 等。
[ ] 每一项的符号方向明确：越大越保守，还是越大越好。
[ ] 每一项的单位或量纲可比较，或说明经过归一化/上界化处理。
[ ] 每一项的估计方式明确：校准误差、Bellman residual、uncertainty propagation、projection loss 等。
[ ] 加和来源明确：union bound、triangle inequality、Lipschitz bound、simulation lemma、Bellman residual decomposition、risk envelope 或经验校准上界。
[ ] 假设边界明确：有限 horizon、局部 Lipschitz、bounded reward、calibrated uncertainty、reference policy continuation 等。
[ ] 使用位置明确：用于 reject、rank、diagnosis，还是报告。
[ ] 消融验证明确：w/o each term，false accept/reject，margin sign flip。
```

更合格的写法：

```text
该预算不是无条件定理，而是局部可校准上界。它将真实执行改进与模型内预测改进之间的差异分解为 rollout 误差、终端 continuation debt、执行投影损失与统计不确定性。四项可由 Bellman residual、anchor-tube distance、局部 Lipschitz 投影损失和 uncertainty calibration 分别估计。若任一项无法校准，计划不得写成已验证改进，只能进入诊断或回退分支。
```

### 15.7 物理可执行风险与 benchmark 约束的真实性规则

“可行性风险”应根据场景精确定义。若涉及机器人、具身智能、工业控制，优先使用更专业的表达：

```text
物理可执行风险 / physical executability risk
闭环可执行风险 / closed-loop executability risk
执行约束风险 / execution-constraint risk
接触与执行器约束风险 / contact-and-actuator constraint risk
```

推荐定义：

```text
物理可执行风险指候选动作片段在真实或高保真仿真闭环中触发的执行层风险，包括碰撞、关节/速度/力矩边界、接触失稳、动作突变、执行器饱和、任务中断以及安全保护触发等。
```

真实性边界必须写清楚：

```text
许多 world model 或 offline RL benchmark 并不显式建模真实物理约束，而是通过 reward、success/failure、cost、termination、constraint violation 或环境异常间接体现风险。
因此，若本文将风险显式纳入 WAM 或执行接口，应把它写成研究贡献或评测扩展，而不是暗示所有已有 world model 都已经处理了物理约束。
```

禁止笼统写：

```text
表示碰撞、越界、接触失稳、执行器过载等可行性风险。
```

应改为：

```text
该变量刻画候选动作片段的物理可执行风险，用于估计其在闭环执行中触发碰撞、运动学或动力学边界、接触不稳定、执行器饱和以及安全终止的可能性。
```

### 15.8 指标体系必须具体、可定义、与 claim 对齐

实验指标不能只列“成功率、回报、时延”。每个指标必须说明：

```text
指标定义；
对应哪个 claim；
为什么适合该任务；
在哪个 benchmark / 真实系统上可测；
与 baseline 是否公平；
失败时如何解释。
```

#### 15.8.1 RL / WAM / Offline RL 指标

```text
success rate / task completion rate：任务完成比例。
normalized return：按 benchmark 归一化的回报。
average return：原始累计回报。
constraint violation rate：约束违反比例。
episode failure / early termination rate：异常终止比例。
OOD false accept rate：高预测收益但执行失败的接受比例。
false rejection rate：本可成功但被拒绝的比例。
Bellman lower-bound margin：预测改进减去误差预算后的裕度。
tail debt / terminal continuation debt：rollout 终点 continuation 不可靠程度。
calibration error：预测风险或成功概率与真实频率的差异。
rollout error stratification：常见区域、边界区域、失败前区域的模型误差。
```

#### 15.8.2 控制与机器人执行指标

```text
IAE = ∫ |e(t)| dt：累计绝对误差。
ISE = ∫ e(t)^2 dt：累计平方误差。
ITAE = ∫ t|e(t)| dt：对后期误差更敏感的时间加权绝对误差。
overshoot：超调量。
settling time：调节时间。
rise time：上升时间。
steady-state error：稳态误差。
control effort：控制能耗或动作幅值积分。
jerk：动作三阶导或离散动作变化率，用于平滑性。
SPARC / spectral arc length：运动平滑性指标，可用于轨迹平滑评价。
latency：单步推理时延、规划时延、约束投影时延。
actuator saturation rate：执行器饱和比例。
contact instability rate：接触任务中的失稳比例。
```

指标选择规则：

```text
若论文主张“控制品质更好”，必须至少包含误差积分、超调/调节时间或动作平滑性之一。
若主张“可信执行”，必须包含 false accept / fallback / violation / recovery 相关指标。
若主张“实时部署”，必须包含 latency、candidate count、rollout count 或 compute cost。
若主张“world model 更适合控制”，必须包含 task-aware prediction、risk calibration 或 Bellman margin 指标。
```

### 15.9 原创性与既有路线关系表

研究计划或方法论文必须有一个小表格说明：本文与已有路线的关系。表格不必长，但必须避免“看起来全是凭空原创”的问题。

推荐表头：

| 路线 | 已有工作解决什么 | 局限 | 本文承接什么 | 本文改变什么 |
|---|---|---|---|---|
| World models / MBRL | 学习动态模型并用于 planning | 预测准确不等于 Bellman 备份可靠 | 采用 WAM 表征动作后果 | 加入可完成改进判据 |
| Offline RL pessimism | 处理分布外乐观估计 | 多为单步策略或价值函数 | 使用保守改进思想 | 扩展到 action chunk 和 terminal debt |
| Diffusion / flow policy | 生成多峰动作或轨迹 | 生成能力不提供执行保证 | 作为局部 proposal/refinement | 由改进包络决定接受 |
| MPC / shielding | 处理约束与安全执行 | 不直接解决离线 WAM 外推 | 借鉴投影/回退接口 | 将投影损失纳入改进证据 |

该表的功能不是“凑表格”，而是说明：本文不是随机组合，而是把已有路线中分散的对象统一到一个核心判据中。

### 15.10 图表与版式全局硬约束

图、表、公式、段落排版必须经过全局检查。以下问题一律视为 `format_or_layout_error`：

```text
图中文字超出框体；
图中标点符号单独占一行；
图中几个字被强行挤成一列；
图内重复出现与 caption 相同的总标题；
图中模块名与正文术语不一致；
箭头关系不表达真实流程、因果、依赖或数据流；
表格列宽导致术语断裂、公式破碎或含义不清；
公式过长造成越界、重叠、编号错位；
每小节第一段无缩进而后续段落有缩进，造成模板不一致；
中英文混排导致空格、断行、标点异常；
PDF 中出现 [?]、??、undefined reference、undefined citation。
```

图表生成规则：

```text
[ ] 图内不放总标题，总标题交给 caption。
[ ] 所有框体必须能完整包裹文字。
[ ] 文字优先使用短语，不用长句。
[ ] 术语必须与正文完全一致。
[ ] 流程图只显示核心逻辑，不堆所有细节。
[ ] 若图内文字较多，宁可拆成两张图或改成表格。
[ ] 生成 PDF 后必须渲染检查，而不是只看 LaTeX 源码。
```

### 15.11 中文语言全局 linter：去除 AI 味、口语化和不专业表达

以下词句在正式论文、研究计划和科研申请中默认禁止或强烈慎用；若出现，必须搜索全文并替换：

```text
接住、兜住、卡住、抓手、路线感、打法、套路、堆东西、补数、硬凑、拍脑袋；
这个形式有意保持简洁、这个设计很自然、显然、很明显、其实、简单来说、换句话说；
不是……而是……（高频使用）、并不意味着、不仅……而且……（机械堆叠）；
逻辑闭环（过度使用时）、AI味道、工程上很方便、看起来合理、比较稳；
这个模块负责、这个东西、这些内容、某种程度上、从某种意义上、可以说。
```

替换原则：

```text
口语词 → 学术对象：接住 → continuation / 后续控制可完成；补数 → 优化 / 数据补充 / 模型修正。
模糊判断 → 可检验判断：看起来稳定 → 约束违反率降低 / false accept rate 下降。
工程描述 → 方法对象：最后挡一下 → 执行投影与回退仲裁。
元话语 → 直接陈述：这个形式有意保持简洁 → 删除，直接说明优化问题含义。
```

每次最终交付前必须运行语言检查：

```text
[ ] 是否存在口语化动词？
[ ] 是否存在自我评价式句子？
[ ] 是否存在“这个/这些/东西/方案”等指代不清？
[ ] 是否存在连续短句导致逻辑割裂？
[ ] 是否存在术语前后不一致？
[ ] 是否存在把工具写成主线、把主线写成工具？
```

### 15.12 段落缩进、章节一致性与模板纪律

若目标是 Word / LaTeX / PDF 正式文稿：

```text
[ ] 每个小节第一段是否与普通段落保持一致缩进，除非模板明确禁止？
[ ] 标题层级是否统一？
[ ] 小节不能只有一个孤立下级标题。
[ ] 章节标题与正文承诺一致：若说“三条主线”，后文不能出现四条独立主线。
[ ] 图、表、公式编号必须递增且正文引用准确。
[ ] 不得因为套模板删除原稿关键内容、图、公式、参考文献。
```

### 15.13 预期成果写作规则

预期成果应具体、可信、不过度承诺。避免反复罗列数据集或 benchmark 名称。推荐包含：

```text
时间边界：例如 12 个月完成主体实验与论文投稿版本。
论文目标：面向 ICLR / ICML / NeurIPS 等顶级会议投稿；若不确定，用“力争/面向”而非保证录用。
代码与数据：投稿前完成内部整理，预印本或接收后公开核心训练、评测和复现实验脚本。
博士研究价值：整理为博士阶段研究的重要组成部分，而不是空泛说“形成博士论文初稿”。
阶段性产出：方法原型、评测协议、消融报告、失败案例库、开源仓库、论文稿件。
```

不合格写法：

```text
形成若干成果；
在多个任务集上验证；
具有重要理论和应用意义；
形成博士论文初稿。
```

### 15.14 Proof engine 增强版：理论完整性审查

在原 proof audit 基础上，增加以下审查项：

```text
THEOREM_OR_OBJECT_NORMALIZATION
- 本文真正提出的对象是什么？
- 它是集合、算子、下界、风险包络、误差预算、选择规则，还是系统协议？

LINEAGE_TABLE
- 每个模块对应哪些已有研究路线？
- 本文承接了什么，改变了什么？

NON_HEURISTIC_CHECK
- 该设计是否只是直觉拼接？
- 是否存在数学、控制、几何或统计意义？
- 加权、阈值、预算、过滤条件是否可解释？

ASSUMPTION_AND_FAILURE_TABLE
- 成立需要哪些假设？
- 假设失败时会产生什么错误？
- 系统如何诊断或回退？

CLAIM_TO_METRIC_MAP
- 每个 claim 对应哪个实验指标？
- 指标是否足够具体？
- baseline 是否同层、同预算、公平？

FIRST_ERROR_WINS
- 首个阻断论文成立的错误是什么？
- 是主线错误、对象错误、证据错误、文献错误、公式错误、版式错误，还是语言错误？
```

增强版输出 verdict：

```text
verified_research_plan_candidate
verification_pass_with_stated_assumptions
verification_incomplete_due_to_theory_gap
verification_incomplete_due_to_evidence_gap
fatal_method_is_heuristic_combination
fatal_citation_distribution_error
fatal_layout_or_language_error
```

### 15.15 面向研究计划书的专门规则

研究计划书不同于已完成论文，不能虚构实验结果，但必须体现博士水平的研究判断。

研究计划书必须做到：

```text
[ ] 立题依据说明科学问题，而不是只说明应用很重要。
[ ] 文献综述体现已有路线、局限与本文承接关系。
[ ] 研究内容不是任务清单，而是可递进的问题链。
[ ] 研究方法说明设计原因、理论依据和验证方式。
[ ] 技术路线不是流程图堆叠，而是“问题—对象—算法—验证—风险处理”。
[ ] 创新点不写“首次提出/显著提升”这类未验证表述，而写“拟定义/拟建立/拟验证”。
[ ] 预期成果具体到论文、代码、评测协议、时间节点，但不保证录用或虚构结果。
```

### 15.16 修订执行顺序

当用户要求对完整论文或研究计划书进行大修时，必须按以下顺序，而不是先润色语言：

```text
1. 锁定基底版本与不可删除内容：页数、公式、图、参考文献、模板结构。
2. 抽取中心 claim 与研究对象。
3. 检查文献综述分布与理论谱系。
4. 检查方法设计依据与非启发式程度。
5. 检查公式语义、假设、估计方式和消融。
6. 检查图表、指标、实验与 claim 对应。
7. 检查创新点和预期成果是否同步更新。
8. 最后做中文 writing pass 和全局版式检查。
9. 编译/渲染/引用/公式重复检查。
10. 输出 proof record，明确已完成与未完成边界。
```

禁止先进行“语言润色”来掩盖主线错误。

# S340 v4.2 English Addendum: Global Theoretical and Revision Constraints

## E15.1 Design Justification Contract

Every core method component must be justified as a research object rather than a heuristic module. A valid design must specify:

```text
object definition;
research lineage;
mathematical/statistical/control-theoretic meaning;
which research question it answers;
which failure mode it mitigates;
assumptions required for validity;
metrics and ablations used for verification.
```

A method is invalid as a main contribution if it only says “we combine A, B, and C” without defining why the combination is necessary and what claim it tests.

## E15.2 Distributed citation rule

References must not be concentrated only in Related Work. They should support:

```text
problem motivation;
formal setup;
method design;
formula interpretation;
metric selection;
baseline fairness;
innovation positioning.
```

If the Method and Evaluation sections contain major design decisions but no supporting literature, the draft has a citation-distribution error.

## E15.3 Non-heuristic formula rule

Any additive budget, weighted score, thresholded set, or filtering rule must explain:

```text
semantic meaning of each term;
sign and scale;
estimation procedure;
assumptions;
whether it follows from a bound, decomposition, residual, calibration, or empirical proxy;
where it enters the algorithm;
which ablation tests it.
```

Otherwise, it must be described as a heuristic engineering choice rather than a theoretical object.

## E15.4 Physical executability and benchmark caveat

In robotics, embodied intelligence, and industrial control, feasibility should be expressed as physical executability risk when appropriate. The draft must not imply that all world-model benchmarks explicitly model physical constraints. Many benchmarks expose risk indirectly through reward, cost, termination, failure, or constraint violation. If a paper explicitly models physical constraints, that modeling choice should be positioned as part of the contribution.

## E15.5 Metric specificity rule

Metrics must be domain-specific and claim-aligned. For RL and WAM, consider success rate, normalized return, constraint violation, calibration error, false accept/reject rate, Bellman margin, tail debt, rollout error, and latency. For control and robotics, consider IAE, ISE, ITAE, overshoot, settling time, control effort, jerk, SPARC, actuator saturation, and contact instability. Each metric must state what claim it tests.

## E15.6 Layout and language linter

Final manuscripts must check for:

```text
text overflowing figure boxes;
standalone punctuation lines;
broken Chinese/English line wrapping;
duplicate figure titles inside figures and captions;
inconsistent indentation;
undefined citations/references;
colloquial or AI-like expressions;
ambiguous pronouns and vague nouns.
```

## E15.7 Research-plan-specific output rule

For research proposals, expected outcomes should be concrete but honest: target venues, release plan, timeline, scripts/protocols, and doctoral-research contribution. Do not guarantee acceptance or fabricate completed results.
